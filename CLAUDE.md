# Google Reviews Analysis

## What this project is

An analysis of a Google review dataset. The question, the audience and the definition of done are in `docs/question.md`. Read that file before doing any work. If it is still a blank template, help the student fill it in first.

## Where things live

| Path | What it holds |
|---|---|
| `docs/question.md` | The question, who it is for, what "done" means |
| `docs/data_dictionary.md` | Every column: meaning, type, known problems |
| `docs/analysis_plan.md` | The ordered steps of the analysis and their status |
| `DECISIONS.md` | Every analytic choice, with alternatives and reasons |
| `docs/findings.md` | Results, each traced to code and decisions |
| `data/raw/` | Original files, never edited |
| `data/interim/` | Partly cleaned data, safe to delete and rebuild |
| `data/processed/` | Analysis-ready tables |
| `notebooks/` | Numbered exploration notebooks |
| `src/` | Reusable code that notebooks import |
| `outputs/figures/`, `outputs/tables/` | Generated by code, never hand-edited |
| `reports/` | The final write-up or slides |

## Rules

1. **Raw data is read-only.** Never write to, rename or delete anything in `data/raw/`. Cleaning reads from `raw/` and writes to `interim/` or `processed/`.
2. **Decide before coding.** Any choice that could change a result (a filter, an exclusion, a recode, a metric definition, a model, a threshold) gets an entry in `DECISIONS.md` before the code is written. If the student has not made the choice yet, lay out the options and trade-offs and ask. Do not choose silently.
3. **Plan before analysing.** Each piece of work maps to a step in `docs/analysis_plan.md`. If it does not, update the plan first.
4. **Every number is traceable.** Anything in `outputs/` or `docs/findings.md` is produced by code in this repo. Each finding names the file that produced it and the decision IDs it depends on.
5. **Count rows.** Report the row count before and after every filter, join and deduplication. An unexplained change in row count stops the work until it is explained.
6. **Protect reviewers.** No reviewer names, profile links or user IDs in outputs, findings, reports or commits. Quote review text only when the point needs it, and never alongside anything that identifies the author.
7. **Data stays out of git.** `data/` contents are ignored. Record where the data came from in `data/README.md` so someone else can fetch it.
8. **Claims match the evidence.** People who leave reviews choose to do so, so they are not a random sample of customers. Describe patterns as associations unless the design supports more, and say what the data cannot show.

## Working with the student

The student owns this analysis. Explain what each piece of code does in plain language. Point out results that look surprising or too clean before moving on. Do not write a conclusion into `docs/findings.md` that the student has not seen and agreed with.

## Conventions

- Language: Python. Packages are listed in `requirements.txt`; add a package there when you first use it.
- Notebooks: `NN_short_name.ipynb`, numbered in the order they run (`01_load_and_check.ipynb`).
- Figures: `fig_NN_short_name.png`. Tables: `tab_NN_short_name.csv`.
- Decisions: `D-001`, `D-002`, and so on. IDs are never reused.
- Commits: one logical change each, with the decision ID in the message when one applies (`Drop duplicate reviews (D-003)`).
